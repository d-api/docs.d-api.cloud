Webhooks notify your system in real time about what happens in each
unofficial WhatsApp **session**: received and sent messages, status changes,
connection events, chat/contact updates and group activity.

## Per-session configuration

Each session has its own webhook configuration, with two delivery modes:

<AccordionGroup>
  <Accordion title="single — one URL for all events">
    All **enabled** events of the session are sent to the same URL.
    Useful when a single endpoint handles all the processing.
  </Accordion>
  <Accordion title="per_event — one URL per event">
    Each event has its own `webhookUrl`, so you can route different events
    to different endpoints.
  </Accordion>
</AccordionGroup>

Regardless of the mode, each event has:

<ResponseField name="enabled" type="boolean">
  Turns delivery of the event on or off. **Disabled events are not sent**.
</ResponseField>

<ResponseField name="webhookUrl" type="string">
  Destination URL of the event (in `per_event` mode) or inherited from the single
  configuration (in `single` mode).
</ResponseField>

## Common envelope

Every webhook arrives with the same envelope. The event-specific content
is in `data`.

```json
{
  "event": "messages.received",
  "sessionId": "my-session",
  "data": { "...": "event-specific" },
  "timestamp": "2026-01-24T22:51:32.601Z",
  "traceId": "c17dee440402792623e3ad6d925cb000"
}
```

<ResponseField name="event" type="string" required>
  Event name (e.g. `messages.received`).
</ResponseField>

<ResponseField name="sessionId" type="string" required>
  ID of the session that originated the event.
</ResponseField>

<ResponseField name="data" type="object" required>
  Event-specific content. See each event's page.
</ResponseField>

<ResponseField name="timestamp" type="string" required>
  Date and time of delivery in ISO 8601 (UTC).
</ResponseField>

<ResponseField name="traceId" type="string">
  Identifier for end-to-end tracing. Useful in logs and support requests.
</ResponseField>

## Headers

| Header | Value |
|--------|-------|
| `Content-Type` | `application/json` |
| `User-Agent` | `Deliverify-Webhook/1.0` |

<Note>
  This product does **not** send an HMAC signature with webhooks. To restrict the
  origin, we recommend using a secret URL (with a token in the path) and/or validating the
  `User-Agent` and the expected `sessionId`.
</Note>

## Delivery and reliability

<AccordionGroup>
  <Accordion title="Retries (7 attempts, exponential backoff)">
    On failure, delivery is retried up to **7 times** with exponential
    backoff: approximately **5s, 10s, 20s, 40s, 80s and 160s** between
    attempts.
  </Accordion>
  <Accordion title="Permanent failures (404 / 410)">
    HTTP **404** or **410** responses are treated as a **permanent failure**:
    delivery is no longer retried for that URL.
  </Accordion>
  <Accordion title="Timeout">
    Each attempt has a **30-second** timeout. Slow endpoints may be
    considered a failure and be retried.
  </Accordion>
  <Accordion title="Circuit breaker">
    There is a **per-URL circuit breaker**: URLs that fail repeatedly are
    temporarily paused to avoid overload.
  </Accordion>
  <Accordion title="Deduplication">
    Events go through **Redis-based deduplication** (5-minute TTL), reducing
    duplicate deliveries of the same event within a short interval.
  </Accordion>
</AccordionGroup>

<Warning>
  Respond quickly with a **2xx** status. Do heavy processing
  asynchronously (queue/worker) and acknowledge receipt as soon as possible to
  avoid timeouts (30s) and unnecessary retries.
</Warning>
